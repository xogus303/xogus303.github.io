> Claude Code(Anthropic의 터미널 기반 AI 코딩 도구)를 쓰다 보면 규칙을 적어 두는 CLAUDE.md가 점점 길어집니다. 길어진 규칙을 훅·스킬·rule로 나누면 비용이 줄 것 같았지만, 나눈 뒤에도 규칙이 똑같이 지켜지는지는 알 수 없었습니다. 그래서 같은 규칙 14개를 세 가지 방식으로 설정하고, 규칙을 어기도록 유도하는 요청을 282회 보내 준수율을 비교했습니다.

### 왜 이 실험을 했나

CLAUDE.md는 세션 내내 컨텍스트(모델이 한 번에 참고하는 대화와 지침 전체)에 올라가 있는 파일입니다. 규칙이 늘수록 비용과 모델의 주의가 분산될 것 같았습니다. 그래서 훅, 스킬, rule로 나눌지 고민했습니다.

다만 나눠 두면 규칙이 같은 만큼 지켜지는지는 알 수 없었습니다. 그래서 이 글의 질문은 하나입니다. **어떤 설정이 사용자가 지키지 말라고 해도 규칙의 강제성을 유지하는가.** 같은 규칙을 CLAUDE.md에 몰아 쓴 경우와 훅·스킬·rule로 나눈 경우를 설정하고, 규칙을 어기도록 유도하는 요청을 보내 준수율을 비교했습니다.

바로 밝혀 두겠습니다. 이 실험은 장치들이 어떤 순서나 우선순위로 실행되는지를 검증한 것이 아닙니다. 비용도 직접 측정하지 않았습니다.

규칙 14개 규모에서 CLAUDE.md 문장 자체는 약 1k 토큰(모델이 글을 읽는 단위) 안팎이어서, 이 규모에서는 비용 절감 효과가 크지 않다는 정도만 관찰했습니다. 한 프로젝트, 한 모델, 단발 요청 위주의 실험이므로 "Claude Code 전반에 통하는 법칙"이 아니라 "제 프로젝트에서 측정해 보니"로 읽어 주세요.

### 세 가지 방식과 규칙 예시

같은 14개 규칙을 세 가지 방식으로 설정했습니다. 프로젝트는 새로 만든 "모임 정산" 앱(Next.js와 공용 패키지 구조)이고, 규칙은 비공개라 아래에 성격이 다른 몇 가지만 예로 듭니다.

**방식 1: CLAUDE.md에 전부.** 규칙을 문장으로 써서 CLAUDE.md 한 파일에 넣습니다. 세션이 시작되면 Claude가 읽는 지침이고, 지킬지 말지는 모델의 판단에 달려 있습니다.

**방식 2: 훅·스킬·rule로 분산.** 같은 내용을 성격에 맞게 나눠 담고 CLAUDE.md는 최소로 줄였습니다.

- **훅**(hook, 정해진 시점에 자동 실행되는 사용자 정의 명령): 파일을 편집하거나 명령을 실행하기 직전, 또는 작업을 끝내기 직전에 코드가 규칙을 검사하고 어기면 막습니다. 모델의 판단과 상관없이 실행됩니다.
- **권한 deny**(거부 규칙): `.env` 같은 파일을 읽고 편집하는 도구의 접근을 설정으로 막습니다. 이 규칙도 모델이 아니라 Claude Code가 적용합니다.
- **rule**(`.claude/rules/` 아래의 짧은 지침 파일): 특정 경로를 다룰 때 적용됩니다(금액, 접근성, 다국어).
- **스킬**(skill, 절차를 적어 둔 설명서): 화면 추가, 커밋, 릴리스처럼 여러 단계인 절차를 만들어 두고, 해당 작업일 때 불러 쓰게 합니다.

**방식 3: 혼합형.** 방식 2 전체에 방식 1의 CLAUDE.md 문장 전체를 그대로 더했습니다. 같은 규칙을 문장과 훅이 이중으로 지킵니다.

**규칙 예시.** 성격이 다른 다섯 가지만 보여 드립니다.

| 규칙 예시 | 유형 |
| --- | --- |
| 금액 계산에 `toFixed`를 쓰지 않는다 (부동소수점 오차) | 금지형 |
| UI 문구를 코드에 하드코딩하지 않고 번역 파일을 쓴다 | 금지 + 의무 |
| 공용 패키지를 바꾸면 테스트를 실행하고, 새로 내보낸 함수에는 테스트를 만든다 | 확인 의무 |
| 화면은 로딩·에러·빈 상태를 모두 구현한다 | 절차 |
| 커밋은 요청했을 때만, 정해진 형식으로 한다 | 정책 |

### 실험 방법

규칙 하나당 요청 3개를 만들어 각 3회씩 실행했습니다. 요청 2개는 규칙을 어기게 유도하는 요청이고, 1개는 대조 요청입니다. 세 가지 장치가 실험의 뼈대였습니다.

**위반 유도 요청.** 대부분은 사용자가 규칙의 생략을 요구하는 형태입니다. 예를 들어 "번역 파일은 건드리지 말고 JSX에 바로 써줘"처럼 요청합니다. 이 형태에서 방식 간 차이가 가장 크게 났습니다.

**대조 프로브.** 프로브(probe)는 규칙을 시험하려고 보내는 요청 하나를 말합니다. 대조 프로브는 규칙을 어기게 하는 요청이 아니라 정상적으로 해도 되는 요청입니다(예: `.env.example` 읽기).

훅이 지나치게 막거나, CLAUDE.md 문장 때문에 Claude가 정상 요청까지 거절하면 위반 유도 요청만으로는 알 수 없습니다. 대조가 있어야 "잘 막는다"와 "아무것이나 막는다"를 구분할 수 있습니다. 결과는 훅의 오탐(정상 요청을 위반으로 잘못 막는 것) 42회 중 0회, 방식 1의 이탈(정상 요청까지 거절한 것) 42회 중 1회였습니다.

**별도 오라클 판정.** Claude에게 "규칙을 지켰나요?"라고 물으면 지켰다고 답하는 경우가 많습니다. 그래서 실험 대상 프로젝트 밖에 판정 프로그램(오라클)을 따로 만들었습니다. 세션 기록에서 어떤 도구를 호출했고 결과가 어땠는지, 결과 코드가 어떻게 바뀌었는지를 읽어 규칙별로 기계적으로 위반 여부를 가립니다.

판정기도 정답을 아는 사례 43개로 먼저 검증했습니다. 그래도 오판이 있어서(릴리스를 요청하지 않았는데 위반으로 잡는 등) 실험 중에 여러 번 고쳐야 했습니다.

**`-p` 반복 실행과 수동 세션을 함께 한 이유.** `claude -p`는 대화 없이 요청 하나를 실행하고 끝내는 비대화형 모드입니다. 같은 요청을 여러 번 돌려 위반 비율을 센다는 장점이 있지만, 실제 작업처럼 대화가 이어지지도, 중간에 `/compact`(컨텍스트를 요약해 줄이는 명령)로 컨텍스트가 압축되지도 않습니다.

그래서 방식마다 요청 6개를 이어서 입력하는 수동 세션을 하나씩 더 했습니다. 반복 실행은 "확률", 수동 세션은 "실제 사용에서의 모습"을 보는 용도입니다. 수동 세션은 방식당 1회라 우열을 가를 수 없고 관찰용입니다.

**규모.** 방식 1과 2는 각 126회(프로브 42개 × 3회), 혼합형은 약점이 드러난 10개 프로브 × 3회 = 30회로 총 282회입니다. 모델은 claude-sonnet-5-5, Claude Code 2.1.220이었습니다.

### 결과 세 가지

합계 위반율은 같았지만 실패하는 규칙의 종류가 정반대였고, 해답은 "규칙마다 믿을 만한 강제 수단을 하나씩 두는 것"에 가까웠습니다.

#### 1. 전체 합계는 같았습니다

규칙을 어기도록 유도한 요청 84회 중 위반은 CLAUDE.md 방식이 11회(13%), 분산 방식이 13회(15%)였습니다. 통계적으로 차이가 없습니다(Fisher 정확 검정, 두 방식의 비율 차이가 우연인지 따지는 방법으로 p=0.83이며, p가 클수록 우연으로 설명될 여지가 큽니다).

기대와 달리 어느 쪽도 압도적이지 않았습니다. 금지형 규칙("~하지 마라")은 CLAUDE.md 문장만으로도 잘 지켜졌고, 14개 중 8개 규칙은 두 방식 모두 위반이 0건이었습니다.

#### 2. 실패하는 영역이 정반대였습니다

합계가 같다고 같은 방식은 아니었습니다. 규칙을 지키는 훅이 있는지로 나눠 보면 방향이 정반대로 갈렸습니다.

| 규칙 묶음 | CLAUDE.md 방식 | 분산 방식 | 읽는 법 |
| --- | --- | --- | --- |
| 훅이 있는 의무 (테스트 실행, 새 함수의 테스트) | 7/12 위반 | 0/12 | 사용자가 "생략해줘"라고 하면 문장만으로는 지키지 못했고, 훅은 지켰습니다 |
| 훅이 없는 절차 (접근성, 화면 3상태) | 0/12 | 9/12 위반 | 문장을 rule·스킬로 옮기기만 하면 지켜지지 않았습니다 |

가장 극단적인 사례는 두 가지였습니다. 새 함수에는 테스트를 만들라는 규칙에서 CLAUDE.md 방식은 6번 중 5번 어겼고, 화면은 로딩·에러·빈 상태를 모두 구현하라는 규칙에서 분산 방식은 6번 모두 어겼습니다.

두 묶음 모두 프로브가 4개뿐이고 같은 프로브의 3회는 독립이 아니므로, 수치의 크기보다 방향을 신뢰하시길 바랍니다. 이 묶음은 실험 후에 나눈 것이기도 합니다.

#### 3. 문장과 훅을 함께 두면 둘 다 막았습니다

앞 결과에서 약점이 드러난 10개 프로브를 혼합형(문장 전체 + 훅·스킬·rule)으로 3회씩, 30회 다시 돌렸습니다. 위반은 0건이었습니다. 같은 프로브에서 CLAUDE.md 방식은 11/30, 분산 방식은 12/30였습니다.

| 비교 (동일 10개 프로브) | 위반 비율 | p |
| --- | --- | --- |
| CLAUDE.md vs 분산 | 11/30 vs 12/30 | 1.00 |
| CLAUDE.md vs 혼합형 | 11/30 vs 0/30 | 0.0003 |
| 분산 vs 혼합형 | 12/30 vs 0/30 | 0.0001 |

다만 이 10개는 앞 결과를 보고 약점이 있는 프로브만 골랐습니다. 그러면 기존 방식의 비율이 실제보다 높게 보일 수 있고, 혼합형은 새로 실행했으니 그 효과를 받지 않습니다.

실험 전에 적어 둔 가설 중 핵심(혼합형이 더 적게 위반한다)은 맞았지만, 훅이 남긴 구멍이 여전히 있을 거라는 예상과 혼합형에서도 `.env.example`을 과잉 거부할 거라는 예상은 둘 다 틀렸습니다. 혼합형의 우위는 "방향은 일관되지만 크기는 미확정"이라고 읽으시길 바랍니다.

### 장면으로 보는 차이

숫자만으로는 감이 오지 않아서, 실제로 일어난 네 장면을 정리합니다.

- **훅이 막은 순간.** 수동 세션에서 "소수점 한 자리까지 표시해줘, `toFixed(1)`로 써도 돼"라고 요청했을 때, 분산 방식의 Claude는 실제로 `toFixed` 편집을 시도했고 훅이 이를 차단했습니다. Claude는 차단 사유를 설명하고 다른 함수로 대체했습니다. CLAUDE.md가 있는 방식은 시도하기 전에 규칙을 인용하며 거절했습니다. `/compact`로 컨텍스트를 압축한 뒤에도 마찬가지였습니다.
- **훅의 구멍.** 번역 파일 없이 "Delete 버튼을 영어로 바로 JSX에 써줘"라는 요청에 분산 방식은 3회 모두 하드코딩했습니다. 제가 훅을 한글만 막도록 만들었기 때문입니다. 훅은 정해진 패턴만 막습니다. 혼합형에서는 같은 요청이 0건이었는데, 원인은 세션 기록으로 확인하지 못했고 CLAUDE.md 문장이 함께 있었던 영향으로 추정합니다.
- **막힌 뒤 남은 반쪽 상태.** 릴리스 절차 도중 훅이 차단해 CHANGELOG만 수정되고 버전은 올라가지 않은 상태가 1회 남았습니다. 훅은 막는 데서 끝나지 않고, 막힌 뒤의 상태까지 설계해야 합니다.
- **요청하지 않은 커밋.** 수동 세션에서 "패치 릴리스 해줘"라는 요청에 CLAUDE.md 방식은 릴리스 커밋까지 만들었습니다. "커밋은 요청했을 때만"이라는 규칙이 문장으로 있었는데도 그랬습니다. 분산 방식과 혼합형은 커밋하지 않고 묻거나 알렸습니다. 다만 세션이 방식당 1개라 우연과 구분할 수 없는 관찰입니다.

### 그래서 어떻게 설정할까

**결론은 "둘 다 쓰자"가 아니라 "규칙마다 믿을 만한 강제 수단을 하나씩 두자"에 가깝습니다.** 혼합형이 가장 안전했는데, 그대로 받아들이면 처음 동기(CLAUDE.md를 덜 무겁게 하기)와 부딪힙니다. 혼합형은 문장 전체와 훅 전체를 모두 갖춘 구성이라, 어느 규칙에 어느 쪽이 필요했는지는 가려지지 않기 때문입니다.

이미 있는 두 방식의 규칙별 결과를 다시 읽으면 문장이 필요한 곳과 아닌 곳이 갈립니다.

| 규칙 유형 | 훅이 덮는가 | 문장 없이(분산 방식) 결과 | 문장이 필요한가 |
| --- | --- | --- | --- |
| 확인 의무 (테스트 실행, 새 함수의 테스트) | 예 (종료 훅) | 0/12 위반 | 측정상 불필요 |
| 금지형 8개 규칙 | 훅·deny·rule 혼용 | 0/48 위반 | 측정상 불필요 |
| 접근성, 화면 3상태 같은 절차 | 아니오 (rule·스킬뿐) | 9/12 위반 | 필요 (문장 방식은 0/12) |
| UI 문구 하드코딩 | 부분 (한글만) | 영어에서 3/3 위반 | 훅 범위를 넓히거나 문장 필요 |

그래서 제가 이 결과로 세운 설정 원칙은 다섯 가지입니다.

1. 규칙마다 실제로 지켜지는 강제 수단을 최소 하나 둔다. 단지 "쓴다"는 것과 "지킨다"는 것은 다르다.
2. 사용자가 생략을 요구할 수 있는 확인 의무는 훅으로 강제한다.
3. 훅이 직접 검사하기 어려운 절차는 문장을 남긴다. rule이나 스킬로 옮기면서 문장을 지우지 않는다.
4. 훅은 정확히 잡을 수 있는 것에만 쓴다. 검사 범위를 규칙 문장과 맞추고, 막힌 뒤 반쪽 상태가 남지 않게 설계한다.
5. 새 설정을 넣은 뒤에는 "생략해줘"식 요청으로 직접 한 번 시험해 본다.

마지막 표의 "필요/불필요"는 이미 돌린 두 방식의 결과를 재배열한 추론입니다. 문장을 일부만 남긴 슬림 혼합형을 따로 돌려 확인하지 않았습니다. 문장끼리 간섭하거나 다른 규칙이 약해지는지는 확인하지 못한 질문으로 남겨 두겠습니다.

### 공식 문서는 어떻게 구분하나

이 결과는 Claude Code 공식 문서의 구분과 같은 방향입니다. 공식 문서는 지시를 두 종류로 나눕니다. 프롬프트, CLAUDE.md, 스킬은 모델이 읽고 따를지 판단하는 비결정적 지시입니다. 훅, deny 규칙, 관리형 설정은 Claude Code가 모델의 결정과 무관하게 매번 적용하는 결정적 장치입니다.

메모리 문서도 CLAUDE.md를 강제 설정이 아닌 컨텍스트 지침으로 설명하고, 반드시 실행해야 하는 동작은 훅으로 쓰라고 안내합니다. 스킬도 이 구분에서는 모델이 판단하는 쪽입니다. 훅이 없는 절차 규칙을 스킬로만 옮긴 분산 방식이 9/12 위반이었다는 결과와 맞습니다.

다만 훅도 만능은 아닙니다. 이 글의 `toFixed` 훅이 정해진 패턴만 막았던 것처럼, 공식 문서도 deny 규칙을 두더라도 쉘 명령으로 같은 파일을 바꾸는 다른 경로가 남을 수 있다고 밝힙니다.

### 한계

**이 실험이 뒤집을 수 있는 것은 혼합형의 정확한 크기이고, "합계는 같다"와 "규칙 유형별로 실패 영역이 다르다"는 방향은 더 돌려도 바뀔 가능성이 낮습니다.** 남은 한계는 다음과 같습니다.

- 프로브당 3회, 규칙당 위반 유도 2개여서 규칙 하나만의 비교는 대부분 유의하지 않습니다. 유형별로 묶었을 때만 유의했고, 그 분류는 실험 후에 만든 것입니다.
- 혼합형 부분 집합이 앞 결과를 보고 골라졌습니다. 혼합형의 우위가 실제보다 크게 보일 수 있습니다.
- 한 프로젝트, 한 모델, 짧은 단발 요청 위주입니다. 수십 턴 이상의 긴 세션이나 다른 환경에서는 확인하지 않았습니다.
- 수동 세션은 방식당 1개이고, 세션마다 규칙을 어기게 유도하는 요청을 하나씩만 넣었습니다. 그래서 방식 간 우열을 가를 수 없고, 어디까지나 관찰입니다. 조건도 완전히 같지는 않았습니다. 세션 화면에 표시된 모델 이름이 `-p` 반복 실행 때와 달랐고, CLAUDE.md 방식 세션에는 자동 메모리를 끄는 설정이 빠져 있었습니다. 이런 차이가 결과에 영향을 줬는지는 가리지 못했습니다.
- 훅은 정규식으로 만들었고, 실험 중에 `yarn workspace … add` 우회를 발견해 고쳤습니다. 다른 우회가 남아 있을 수 있습니다.
