> 1편에서는 재고 하나를 두고 벌어지는 경합을 Redis 원자 연산으로 해결했습니다. 그런데 선착순 서비스엔 재고 경합 말고도 풀어야 할 문제가 하나 더 있었습니다 — "누가 먼저 왔는지"를 한 치 오차 없이 매기는 것, 그리고 "한꺼번에 들여보내는 인원"을 뒷단이 감당할 수 있는 만큼으로 조절하는 것입니다. 이 글은 대기열을 만들며 CI에서만 재현된 버그 하나, 입장 인원을 정하는 방식을 고민한 과정, 그리고 입장 속도를 결제 파이프라인의 실제 처리 능력에 맞춰 스스로 늦추게 만든 작업의 기록입니다.

### 대기열이 하는 일

Sunchak의 재고 관문(1편)은 "되면 되고, 안 되면 바로 거절"하는 즉시 판정입니다. 대기열은 그 관문과는 완전히 다른 계층입니다 — 재고를 아예 건드리지 않고, **"언제 관문에 도전할 자격을 주는가"**만 결정합니다.

<aside class="post-aside"><ol>
<li><strong>대기열 진입</strong></li>
<li>입장 처리 워커가 주기적으로 N명씩 허가 → <strong>입장 허가</strong>(TTL 있음)를 받습니다.</li>
<li>허가 안에서만 재고 관문에 도전할 수 있습니다 → 관문 통과 → <strong>HELD</strong>(임시 확보) → 결제 큐 → 확정.</li>
</ol></aside>

자료구조는 Redis **Sorted Set**(ZSet) — 각 원소에 점수(score)를 매겨 정렬된 순서로 보관하는 구조입니다. 사람이 대기열에 들어오면 `ZADD`로 큐에 등록되고, 입장 처리 워커가 주기적으로 `ZPOPMIN`(점수가 가장 작은, 즉 가장 먼저 온 사람)을 꺼내 허가를 내줍니다.

### 같은 밀리초에 두 사람이 도착하면? — 순번 동점 버그

ZSet에 넣을 때 "점수"를 뭘로 매길지가 핵심입니다. 처음엔 가장 직관적인 값 — **도착 시각**(`Date.now()`, 밀리초)을 썼습니다. 먼저 온 사람일수록 시각이 작으니 자연스럽게 순서가 맞을 거라 생각했습니다.

문제는 CI 파이프라인(GitHub Actions)을 처음 돌렸을 때 드러났습니다. "허가 후 재입장하면 새 순번으로 다시 대기한다"는 테스트가 `rank: 1`을 기대했는데 `rank: 0`을 받아 실패했습니다. **로컬에서는 멀쩡하던 테스트가 CI에서만 깨진 겁니다.**

원인을 쫓아가 보니, 두 번의 `join()` 호출이 **같은 밀리초 안에** 끝나면 점수가 동점이 됩니다. Redis ZSet은 점수가 같으면 **멤버 이름을 문자열 사전순으로** 정렬합니다 — 그러면 나중에 도착한 사람의 ID가 사전상 앞이라는 이유만으로, 먼저 온 사람을 앞질러 버립니다.

로컬 환경에서는 이 버그가 거의 안 보였습니다. 매 요청이 Redis까지 네트워크 왕복을 거치면서 자연스럽게 시간 차가 생겨, 두 `join()`이 같은 밀리초에 끝날 일이 드물었기 때문입니다. 반면 CI의 서비스 컨테이너는 왕복이 훨씬 빨라서 동점이 실제로 자주 발생했습니다. **"CI에서만 나는 버그"가 아니라, 로컬은 우연히 운이 좋았을 뿐**이라는 뜻입니다 — 실제 선착순 트래픽이 몰리는 순간에도 똑같이 재현될 수 있는, 이 대기열이 존재하는 이유 자체를 흔드는 공정성 버그였습니다.

고친 방법은 "도착 시각"이라는 애매한 값 대신, Redis `INCR`로 직접 채번한 **단조 증가 정수**를 점수로 쓰는 것이었습니다.

```ts
const rank = await redis.incr(`queue:seq:${eventId}`)
await redis.zadd(`queue:event:${eventId}`, rank, userId)
```

`INCR`은 Redis가 싱글 스레드로 처리하는 명령이라, 동시에 여러 `join()`이 몰려도 **절대 같은 값을 두 번 내주지 않습니다.** 점수가 애초에 동점일 수 없으니, 사전순 정렬로 넘어갈 일 자체가 사라집니다.

> CI에서만 나는 버그를 "환경 탓"으로 넘기지 않고 재현 조건까지 파고든 덕에, 실제 트래픽에서도 터질 수 있던 공정성 문제를 배포 전에 잡을 수 있었습니다.

### 왜 "고정 N명씩"이 아니라 흔들리는 배치로 들여보내는가

입장 처리 워커가 매 틱마다 몇 명을 허가할지도 선택이 필요했습니다. 가장 간단한 방법은 "매번 정확히 20명"처럼 고정된 수를 빼는 것입니다. 하지만 이 프로젝트가 재현하려는 상황 — 재고 1만, 가상 유저 5천 명이 한꺼번에 들어오는 대용량 트래픽 — 에서는 고정 배치 대신 남은 인원의 20%를 평균(λ)으로 잡고, 매 틱 그 평균 근처에서 자연스럽게 흔들리는 값을 뽑는 **변동 배치**를 택했습니다. 근거는 통계적인 사실 하나입니다: 많은 사람이 각자 무작위 순간에 독립적으로 도착하면, 그 도착 수를 합친 값은 설계자가 일부러 흔들어서가 아니라 **독립적인 사건을 합치면 자연히** 평균 근처에 몰리고 극단값은 드물어지는 종 모양을 띱니다(포아송 과정). 고정 배치는 이 자연스러운 흔들림을 인위적으로 눌러버려, 실제 오픈런처럼 "초반에 몰렸다가 점점 잦아드는" 흐름과는 다른 모양이 됩니다.

실제 포아송 분포를 그대로 계산하는 대신, 평균이 어느 정도 크면 포아송이 정규분포(평균 λ, 표준편차 √λ)로 잘 근사된다는 성질을 이용했습니다. 정규분포 난수는 Math.random()이 주는 균등분포 난수 두 개를 **Box-Muller 변환**으로 바꿔 얻습니다.

```ts
function randomStandardNormal(): number {
  const u1 = Math.max(Math.random(), Number.EPSILON) // log(0) 방지
  const u2 = Math.random()
  return Math.sqrt(-2 * Math.log(u1)) * Math.cos(2 * Math.PI * u2)
}

function poissonLikeBatchSize(remaining: number, meanFraction: number, min: number, max: number): number {
  if (remaining <= 0) return 0
  const lambda = Math.min(Math.max(remaining * meanFraction, min), max)
  const raw = Math.round(lambda + Math.sqrt(lambda) * randomStandardNormal())
  const clamped = Math.min(Math.max(raw, min), max)
  return Math.min(clamped, remaining)
}
```

평균을 그냥 쓰지 않고 `[min, max]`로 한 번 자르는 이유는 두 가지입니다. 대기열이 아주 크면 한 틱에 너무 많이 빠져나가지 않게, 아주 작으면 평균(λ)이 0에 가까워져 정규분포 근사 자체가 깨지지 않게 막는 안전장치입니다. 실제 기본값은 평균 비율 20%, 최소 50명, 최대 1,000명, 1초마다 — 이 값들로 매 틱 50~1,000명 사이에서 자연스럽게 흔들리는 수가 허가됩니다.

### 대기 순번은 폴링, 허가되는 순간은 즉시 — 두 흐름을 merge하다

대기열에 들어온 사람에게 "지금 내 순번이 몇 번인지"를 계속 보여줘야 합니다. 여기서 쓴 방법은 **1초 폴링**입니다 — 1초마다 한 번씩 "지금 내 순번이 뭐지?"를 다시 물어봅니다. 완전한 실시간은 아니지만, 순번이 줄어드는 속도 자체가 눈에 띄게 빠르지 않은 상황에서는 충분하고, 구현도 단순합니다.

문제는 **"대기 중 → 허가됨"으로 바뀌는 그 전환 순간**입니다. 이 순간까지 폴링에만 의존하면, 최악의 경우 거의 1초 가까이 "허가됐는데도 화면은 아직 대기 중"으로 보일 수 있습니다. 입장이 허가됐다는 건 사용자 입장에서 가장 중요한 순간인데, 거기서 지연이 체감되는 건 아쉬운 지점이었습니다.

해법은 두 개의 서로 다른 데이터 흐름을 **하나로 합치는** 것이었습니다.

- **폴링 흐름**: 1초마다 "지금 순번이 뭐지?"를 재조회하는 흐름 (평상시 순번 표시를 담당)
- **이벤트 흐름**: 입장 처리 워커가 누군가를 허가하는 **그 순간** 즉시 방송하는 이벤트 버스

RxJS의 `merge` 연산자는 여러 Observable(값이 흘러나오는 스트림)을 하나로 합쳐, **어느 쪽이든 먼저 값을 내보내면 그걸 즉시 내보냅니다.**

```ts
streamStatus(eventId: string, userId: string) {
  const polling$ = timer(0, 1000).pipe(switchMap(() => this.status(eventId, userId)))
  const admitted$ = this.events.ofUser(eventId, userId).pipe(switchMap(() => this.status(eventId, userId)))
  return merge(polling$, admitted$)
}
```

평상시엔 폴링(`polling$`)이 1초마다 상태를 흘려보내고, 워커가 허가하는 순간엔 이벤트(`admitted$`)가 그 즉시 끼어들어 최신 상태를 흘려보냅니다. 평소의 단순함(폴링)과 가장 중요한 순간의 즉시성(이벤트)을 **둘 다** 가져가는 조합입니다.

다만 이 패턴을 "대기 중 순번이 줄어드는 것" 자체에도 똑같이 적용하진 않았습니다. 앞사람이 빠질 때마다 매번 이벤트로 방송하면, 대기자가 많을 때 전원의 상태가 동시에 재조회되는 부담이 생길 수 있어서입니다 — 이 부분은 지금도 1초 폴링에 의존하는 채로 남겨둔 알려진 한계입니다.

### 포아송이 계산한 희망값을 뒷단이 못 받아주면?

그런데 포아송 배치는 **대기열 크기만 보고** 계산합니다 — 결제 파이프라인이 지금 얼마나 여유가 있는지는 전혀 모릅니다. 그대로 두면, 대기열이 크다는 이유만으로 뒷단이 감당 못 할 만큼 많은 인원을 한꺼번에 재고 관문으로 들여보낼 수 있습니다.

관문을 통과한 사람은 곧바로 "확정"이 되는 게 아니라 **HELD**(결제도 확정도 아직 안 된, 재고만 그 사람 몫으로 임시로 붙잡아둔 상태)로 기록됩니다. 이 HELD 상태에는 30초짜리 TTL이 걸려 있어서, 그 안에 결제가 끝나지 않으면 자동으로 회수되고 재고가 반환됩니다. 실제로 포아송 배치만으로 밀어붙였더니, 결제 큐가 밀리는 동안 이미 HELD로 잡힌 사람들의 TTL이 결제보다 먼저 끝나버려서 "결제는 성공했는데 예약은 이미 만료됐다"는 정합성 깨짐이 발생했습니다.

필요한 건 "대기열이 큰가"가 아니라 **"지금 들여보내도 뒷단이 제때 처리할 수 있는가"**였습니다. 여기서 쓴 게 **Little's Law**(`L = λ·W`, 평균 대기 인원 = 도착 속도 × 평균 체류시간)입니다.

```ts
// "지금 이미 결제 처리 중인 인원(L)"이
// "처리량(λ) × 허가창(W)"을 넘지 않을 만큼만 새로 허가한다
const maxInFlight = paymentThroughputPerSec * paymentBurstWindowSec
const availableSlots = Math.max(0, maxInFlight - currentInFlightCount)
const batchSize = Math.min(desiredBatchSize, availableSlots) // 포아송 희망값과 상한 중 작은 쪽
```

포아송이 계산한 "희망하는 배치 크기"와, Little's Law로 계산한 "지금 안전하게 받을 수 있는 자리 수" 중 **작은 쪽**을 최종 배치로 씁니다. 뒷단이 밀리면 입장 허가가 스스로 느려지고, 넘친 인원은 TTL 없는 대기열에서 계속 기다릴 뿐 아무도 조용히 사라지지 않습니다.

공식의 두 변수(λ, W)는 둘 다 추측이 아니라 실측으로 정했습니다.

**처리량(λ) 측정**: 그냥 부하를 걸고 재면 "입장 허가 자체가 이미 속도를 조절하고 있어서" 결제 파이프라인의 진짜 한계를 잴 수 없습니다(측정하려는 대상을 측정 장치가 스스로 제한하는 순환 문제). 그래서 **입장 허가 단계를 완전히 건너뛰고** 측정했습니다 — HELD 예매 3,000건과 결제(Payment) 3,000건을 DB에 직접 만들어 결제 큐에 한 번에 투입(`addBulk`)한 뒤, 처리 완료 시각(`Payment.updatedAt`)의 분포만 관찰했습니다. 결과: **3,000건이 20.2초 만에 처리, 내내 초당 150~165건을 안정적으로 유지**. 여기에 여유 마진을 두고 130을 기본값으로 채택했습니다.

**체류시간(W) 측정**: 처음엔 "결제 job이 처리되는 순수 시간"(3초)만 넣었는데, 실제로는 "사람이 버튼을 누르기까지의 랜덤 지연"까지 HELD 상태로 시스템에 머무는 시간에 포함된다는 걸 놓쳤습니다. 실제 배포 환경의 HELD 체류 시간 분포(p90 14.9초)를 반영해 15초로 재조정했습니다.

### 전체적으로 보면

재고 관문(1편), 대기열(이 편), 그 뒤의 결제 파이프라인은 서로 다른 계층이지만, 셋 다 같은 원칙 하나를 공유합니다 — **"지금 처리할 수 있는 만큼만 받아들이고, 넘치는 건 숨기지 않고 기다리게 한다."** 재고는 Redis 원자 연산이, 입장은 백프레셔가, 순서는 단조 증가 정수가 각자의 층에서 이 원칙을 지킵니다.

> CI에서만 재현되는 버그를 "환경 차이"로 덮지 않고, 대기열이 왜 존재하는지(공정한 순서)까지 돌아가서 원인을 찾았던 게 이번 편에서 가장 오래 걸린 과정이었습니다. 그리고 "뒷단이 못 받아주면 스스로 느려진다"는 설계는, 처음부터 답을 알고 짠 게 아니라 실제로 밀어붙여 정합성이 깨지는 걸 본 뒤에야 나온 결과였습니다.
